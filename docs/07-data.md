# Раздел 7. Данные: загрузка, актуализация и качество

*Закрывает п. 6.6 ТЗ и пп. 3.2.1–3.2.6 ТЗ. Метрики качества и журнал замечаний приведены в приложении Б.*

## 7.1. Состав каталога

На дату документа в каталоге 555 карточек роботов. Каждая связана с исходной платформой через таблицу `product_origin`:

| Источник | Карточек | Как попали в каталог |
|---|---|---|
| Каталог организатора (ФЦ БАС), `fc_bas` | 187 | Загрузка CSV организатора (`import_catalog`) |
| robot.moscow | 308 | Парсер `robot_moscow` (берёт только роботов с ценой) |
| robort.ru | 60 | Парсер `robort` (разделы: сервисные роботы, манипуляторы, уборщики, склад, колёсные платформы) |

Кроме них реализован парсер `robob2b` (robob2b.ru). Последний запуск завершился ошибкой (сайт-источник недоступен или изменил разметку), поэтому карточек из него в каталоге нет.

Реестр источников значений хранит 605 записей: 556 из парсеров, 29 вендоров (страницы производителей), 15 дилеров, 4 оценки по аналогу и запись каталога организатора. Значение каждой характеристики ссылается на источник, а в карточке рядом со значением видны вид источника, издатель, ссылка, дата и цитата (ТЗ 3.2.4, 3.2.5).

Карточки на «дне» иерархии привязаны к процессам (`product_process`), 496 связей; 446 карточек имеют хотя бы один процесс, 109 без процессов пока не участвуют в подборе (`docs/process-assignments-review.md`).

## 7.2. Форматы загрузки

Загрузка выполняется администратором в разделе «Админка → Каталог». Файл передаётся методом `POST /admin/imports` (multipart), API создаёт задание в очереди, воркер его выполняет. Статус и счётчики прогона видны в админке и в `GET /admin/jobs`.

### CSV каталога организатора (`import_catalog`)

Кодировка UTF-8 (BOM допускается), разделитель `;`, одна строка на пару «продукт — сценарий». Строки одного продукта группируются по столбцу `id` (обязательно UUID). Используемые столбцы:

| Столбец | Куда попадает |
|---|---|
| `id` | Внешний идентификатор карточки (`product_origin.external_id`) |
| `Название` | Название (обязательно) |
| `компания` | Производитель |
| `Цена изделия` | Цена, ₽ (форматы «1 500 000», «1,5»; «по запросу» и «—» считаются пустыми) |
| `статус` | Стадия готовности (`operation`, `piloting`, `rnd`) |
| `УГТ` | Уровень готовности 1–9 |
| `описание` | Описание |
| `Регион`, `тип`, `Тип`, `Подтип`, `Отрасль`, `Сценарий`, `Кейсы`, `Рын Потенциал` | Характеристики карточки (`attrs`); `Сценарий`, `Кейсы` и `Отрасль` собираются со всех строк продукта |

### Ручная таблица ТТХ (`import_manual`)

Кодировка UTF-8, разделитель запятая. Одна строка на значение характеристики:

| Столбец | Обязательный | Значение |
|---|---|---|
| `product_slug` | да | Слаг карточки |
| `attr_key` | да | Ключ характеристики (латиница, например `payload_kg`) |
| `label` | нет | Подпись (по умолчанию ключ) |
| `value` | нет | Значение |
| `unit` | нет | Единица |
| `status` | нет | `known` (по умолчанию) или иной статус |
| `source_kind` | нет | `vendor`, `dealer`, `catalog`, `media`, `analogue`, `assumption` (по умолчанию `dealer`) |
| `source_url` | нет | Ссылка на источник |
| `quote` | нет | Цитата из источника |

### Парсеры сайтов

Парсеры запускаются вручную кнопкой в админке (`POST /admin/parsers/{code}/runs`) или по расписанию: для каждого задаётся признак включения и час запуска по Москве (`PATCH /admin/parsers/{code}`). В поставке все три парсера выключены, час запуска по умолчанию 03:00. Воркер раз в сутки ставит в очередь включённые парсеры.

Правила при загрузке (`ingest_records`):

- Карточка узнаётся по паре (платформа, внешний ID); повторный прогон обновляет её, а не создаёт дубль.
- Ручное значение характеристики, введённое администратором, помечено как ручное и **не затирается** следующим импортом (ТЗ 3.2.6).
- Новым карточкам сразу назначается тип решения по правилам классификации; число карточек без типа видно в итогах прогона.
- Карточкам, пришедшим из парсера, процессы не назначаются автоматически: назначение выполняет администратор или миграция пересмотра.

## 7.3. Нормализация значений

Значения характеристик из разных источников приходят в разном виде («от 2 до 4 ч», «1,5 т», «до 90 %»). Скрипт `normalize_catalog` приводит их к единому виду и сохраняет исходную запись:

| Ситуация | Правило |
|---|---|
| Диапазон «2–4 ч», «до 3 часов», «не более 3 ч» | Берётся **верхняя граница**; единицы пересчитываются; исходный текст сохраняется в `normalization_original`, метка `normalization_rule: upper_bound` |
| Единицы (кг, т, ч, мин, м/с, км/ч) | Приводятся к единицам платформы |
| Значение с несколькими режимами | Режимы хранятся раздельно: для времени работы используется значение под полной нагрузкой, для перевозки грузоподъёмность в движении |
| Приблизительное значение, невидимые символы, повторы парсера | Очищаются, признак приблизительности сохраняется |
| Значения без единиц, конфликтующие варианты, описание без числа | **Не превращаются в догадки**, попадают в список замечаний |

Команды: `make audit-platform` (только отчёт, БД не меняется) и `make normalize-platform` (применить и записать отчёт в `reports/`). Итог последнего прогона на 555 карточках: изменено 70, осталось 32 замечания, повторный аудит показал 0 изменений (`platform/docs/catalog-normalization-report.md`).

## 7.4. Как обновить каталог

1. Зайти под администратором, открыть «Админка → Каталог».
2. Загрузить свежий CSV организатора или запустить парсер. Дождаться статуса «выполнено»: воркер работает в фоне, интерфейс можно закрыть.
3. Проверить счётчики прогона (создано, обновлено, пропущено, без типа).
4. Назначить новым карточкам типы решений (раздел «Типы решений → Без типа») и процессы (карточка → «Процессы»).
5. При необходимости внести ручные значения в карточке. Помеченное вручную значение переживёт следующий импорт.
6. Выполнить `make audit-platform` и убедиться, что новых замечаний нет.

Влияние на проекты: подбор и экономика пересчитываются по текущему каталогу при каждом открытии, поэтому изменения каталога сразу отражаются во всех проектах. Версионирования каталога и «замороженных» расчётов нет (раздел 2.7).

## 7.5. Что не решено с данными

Полнота данных остаётся главным ограничением качества подбора: только у 31 % карточек указана грузоподъёмность, у 27 % время работы, у 13 % скорость, у 4 % минимальная ширина прохода, у 1 % высота подъёма; потребляемая мощность указана только у двух карточек (для остальных энергия считается по нормативу 0,9 кВт·ч в час). Из-за этого у большинства пар «робот — процесс» вердикт «Уточнить». Детали, расчёты доли заполненности по каждому полю и журнал замечаний приведены в приложении Б.
