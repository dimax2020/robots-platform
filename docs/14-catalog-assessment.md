# Автоматическая оценка по данным каталога

Опубликованные характеристики используются без `reviewed=true` и без обязательной записи `product_assessment`/`process_assessment`. Карточки, UUID, исходные attrs, источники, связи и миграции не переписываются. Новых моделей количества и финансовых формул этот этап не добавляет.

## Единая цепочка данных

`catalog_assessment.resolve_catalog` строит временную проекцию карточки. Использует известные attrs и опубликованное описание, существующую нормализацию/алиасы и явные формулировки назначения, управления, среды. Название модели, тип, УГТ и связь `product_process` сами по себе не доказывают выполнение операции. Словарь терминов относится к операциям, UUID и названий отдельных моделей в нём нет.

Числа приводятся к каноническим единицам, но исходные значения остаются в `provenance`: status, source_id, сведения об источнике, quote, unit, normalization_original и результат нормализации. Конфликтующие алиасы, неоднозначные единицы, допущения/аналоги не подставляются в обязательную проверку. Явный диапазон/верхняя граница времени работы, скорости или производительности не превращается в гарантированное рабочее значение. Структурированные `conditions` характеристики применяются только при совпадении с параметрами площадки; иначе причина указывает недоказанные условия. Исходные ограничения в описании QR-маркировки, тягача и обязательной WMS также проверяются, опциональная маркировка не становится обязательной.

Assessment остаётся необязательным дополнением для сведений, ещё не представленных в attrs, и настройки требований/модели количества. Его legacy-флаги reviewed/requirements_reviewed не разрешают и не запрещают подбор. Явные структурированные факты в attrs и извлечённые опубликованные сведения проходят один resolver. Расхождения с дополнением assessment дают конкретный конфликт, а не молчаливый выбор источника. Администратор исправляет каталог или устаревшее дополнение; обычный импорт не обязан создавать assessment. API GET/PUT assessment сохраняет совместимость и права администратора. PUT по-прежнему проверяет структуру; исторический reviewed=true с пустым evidence остаётся некорректным документом, но этот флаг не требуется для работы.

## Исполняемые требования

`process_requirements.compile_requirements` объединяет правила процесса в БД с системными ограничениями, без ручного разрешения профиля. Старые hard/conditional-проверки, bindings, явные критичные характеристики и требования оснастки сохраняются. Встроенные требования нельзя удалить пустым legacy required_checks.

Для инвентаризации добавлены обязательные сравнения высоты сканирования с высотой хранения (метры → миллиметры) и минимального прохода с проходом площадки. Сканирующий комплекс с оператором/тягачом рассматривается как отдельный допустимый способ выполнения инвентаризации; это не утверждение полного замещения труда. Явные температурные ограничения площадки проверяются по допустимым температурам изделия.

Если для процесса нет обязательных инженерных правил, результат unknown с `process_checks_missing`. Проверка температуры не заменяет отсутствующую спецификацию операции. Такие процессы требуют разработки правил в системе, а не ручной модерации каждой карточки. Никакого универсального допуска по одной записи о назначении нет.

## Независимые результаты

- `verdict`, `technical_ready`, `reasons` относятся к техническим условиям. Недостающие обязательные сведения дают unknown, установленная несовместимость — fail; conditional сохранён для существующих условных правил. Комплектность поставки и цена не влияют на технический pass. Семейство без выбранного варианта и отсутствие необходимой технической оснастки остаются неопределённостями применимости.
- `count`, `sizing_ready`, `sizing.reasons` относятся к математической модели количества. При наличии достаточных входов модель может рассчитать количество даже для технически несовместимого кандидата; это не разрешает включить его в парк. Новых моделей нет: для инвентаризации count остаётся null.
- `economic_ready`, `economic_reasons` требуют технический pass, положительное количество, положительную цену, известную комплектность и охват цены. Число не подставляется автоматически. Неполный проект не получает точных ROI/окупаемости.

`technical_best_product_id` ранжирует технические pass независимо от цены и количества. `best_product_id` сохраняет прежний контракт выбора только экономически готового кандидата. Технические pass автоматически попадают в сравнение, выбор для экономики остаётся отдельным действием со строгой серверной проверкой. Сохранённые недопустимые ID не заменяются молча.

Ответ кандидата содержит `data_basis=published_catalog_v1`, `resolved_facts` и `provenance`. Runtime и административный предпросмотр используют один resolver и один matcher.

## Интерфейс

На подборе и сравнении отдельно показаны применимость, количество, экономика и причины. В параметрах площадки можно явно задать `qr_marking_ready` и `towing_available`; неопределённость не заменена ответом «да».

Фильтр каталога называется «УГТ ≥ 5, не в разработке» и больше не обещает технической готовности. Сохранённый attrs.ready_for_automatch отображается как историческая отметка и не участвует в алгоритме. Поле autoMatch в адаптере frontend оставлено для совместимости, его смысл — только фильтр УГТ/стадии.

## Реальные инвентаризаторы

Контрольные сведения двух карточек сохранены в `platform/tests/fixtures/inventory-catalog.json`, без изменения исходного SQL snapshot.

| Карточка | Автоматически использовано | Оставшиеся ограничения |
|---|---|---|
| AI Stock Counter 12M | Назначение, indoor, мачта 12 м, 2 ч батареи, перемещение с оператором/тягачом, требования QR | Нет минимального прохода; маркировка и схема перемещения площадки не заданы; старая условная проверка смены 2 ≥ 11 не выполнена. Производительность «от 12 600» не считается точным рабочим значением |
| Инвентаризатор Яндекса | Назначение, автономное мобильное исполнение, indoor, мачта 12,5 м, требования QR | Нет минимального прохода и времени автономной работы; маркировка площадки не задана; «до 30 000» — верхняя граница |

Обе карточки на исходном демоскладе дают unknown по конкретным условиям, без причин об отсутствии reviewed. При высоте хранения 13 м обе получают fail по высоте. Модели количества инвентаризации нет, состав/охват цены не определены — экономика неполная. Положительный результат не создаётся искусственно.

## Проверки и границы

Адресные тесты проверяют положительный допуск опубликованной карточки без assessment/цены/комплектности/модели количества, unknown при пропусках, fail по известным ограничениям, единицы, конфликты, условия эксплуатации, происхождение, отсутствие влияния reviewed и независимость количества от технического отказа. Интеграционный положительный путь проходит публичные match/economy API без product_assessment; реальные карточки проверяются через ту же цепочку.

Итоговая проверка: 248 backend-тестов на отдельной PostgreSQL прошли (одно предупреждение о deprecated TestClient/httpx); общие сценарии выбора Python/TypeScript, предварительное техническое сравнение, frontend typecheck и production build прошли. Исходные поля всех 555 карточек, связи и источники повторно сравнены с контрольной выгрузкой — изменений нет. Рабочая БД и контейнеры не обновлялись.

READ ONLY-проверка исходных демоплощадок: склад — 148 unknown / 14 fail; аэропорт — 142 unknown / 8 fail; больница — 75 unknown / 14 fail. Реальных pass на этих неполных входах по-прежнему нет, однако причины больше не связаны с обязательной модерацией. Это не заменяет адресное заполнение недостающих параметров площадки и характеристик каталога.

Свободный текст не является универсальной инженерной спецификацией: неподдержанные формулировки остаются неизвестными. Следующие задачи — расширение формальных требований для процессов без правил, структурированное представление режимов/диапазонов и конфликтов, новые модели количества. Массовая разметка карточек и разработка этих моделей в текущую задачу не входят.
