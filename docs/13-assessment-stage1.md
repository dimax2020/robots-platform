# Первый этап исправления подбора и экономики

> Историческое описание первого этапа. Обязательные ручные отметки `reviewed` впоследствии исключены из допуска; актуальная архитектура описана в [подборе по данным каталога](14-catalog-assessment.md). Цифры ниже относятся к контрольному прогону этапа 1.

Реализовано 19 октября 2026 года. Изменения закрывают небезопасные допуски, но не заменяют пересмотр каталога и инженерные модели мощности.

## Архитектура

`product_process` по-прежнему хранит потенциальное назначение. Положительный допуск требует отдельно проверенных фактов изделия (`product_assessment`) и достаточного профиля процесса (`process_assessment`). В новых таблицах хранится версионируемый JSON, исходные product/attrs/source/UUID/slug и связи не переписываются.

Порядок проверки:

1. Функция, вид решения, управление, среда, комплектность и оснастка.
2. Подтверждённость профиля и обязательные технические проверки/входы.
3. Совместимая модель расчёта количества с явными единицами и параметрами.
4. Готовность к экономике: только pass, известное корректное количество, положительная цена и подтверждённый охват комплектации ценой.
5. Серверная проверка автоматического или явного выбора, полноты покрытия проекта и независимого исходного труда.

Код: `domain/assessment.py`, `match.py`, `sizing.py`, `formula.py`, `economy.py`; интеграция — `infrastructure/db/taxonomy_repo.py`. У алгоритма нет runtime-зависимости от `reports/`.

### Метаданные

Факты изделия: version=1, reviewed, evidence, solution_kind, control_mode, execution_class, environments, capabilities (коды операций), equipment, configuration_complete, price_complete.

Профиль процесса: version=1, requirements_reviewed, reviewed, evidence, allowed_kinds, allowed_controls, environments, required_equipment, critical_robot_keys, critical_site_keys, required_checks, sizing.

`requirements_reviewed` разрешает использовать подтверждённые ограничения среды/исполнения для отрицательного допуска. `reviewed` означает, что достаточность всего технического профиля проверена. Непроверенный профиль не даёт pass. Для положительного допуска обязательны списки допустимых видов/управления/среды, критичных входов и характеристик, обязательных hard-проверок, сами рабочие правила и evidence.

Неподтверждённые факты не превращаются в подтверждённый fail. Семейство без конкретного варианта требует уточнения; компонент, ПО и операторская техника не являются комплектным автономным решением. Тип каталога и слова в названии сами по себе не подтверждают capability.

Редактирование доступно только администратору:

- `GET/PUT /api/v1/admin/products/{slug}/assessment`;
- `GET/PUT /api/v1/admin/processes/{code}/assessment`.

PUT заменяет служебный документ, проверяет поля/типы/версию и наличие evidence для подтверждения. Обычный импорт и кабинет поставщика не подтверждают эти сведения автоматически. Импорт ТТХ не затрагивает новые таблицы. Исходные технические значения и их источники сохраняются.

Пример полностью подтверждённого **синтетического** комплекта и профиля находится в `platform/tests/test_assessment.py`; это тестовые сведения, не паспорт реального изделия.

### Количество

Старые count_formula/count_inputs и привязки сохранены для совместимости, но больше не запускаются автоматически для всех изделий процесса. Рабочие результаты подбора и предпросмотр используют реестр моделей `sizing.py`.

Пока реализован только `mobile_cycle_v1`: execution_class=mobile_transport, flow_unit=items/day, quantity_unit=machines. Нужны явные flow_per_day, route_len_m (односторонний маршрут), t_load_s, t_unload_s, batch_size, availability (доля 0…1), reserve_count, shift_hours, shifts_per_day, speed_loaded_ms и speed_empty_ms. Входы задачи накладываются на параметры площадки; скорости берутся из карточки. Все числовые значения должны быть конечными, в указанных канонических единицах.

Цикл = путь/скорость с грузом + путь/скорость без груза + загрузка + выгрузка. Количество = ceil(поток / batch × цикл / доступное рабочее время) + **явно заданный** резерв. По умолчанию не подставляются ни 80 секунд, ни 0,82, ни резервная машина. Для неизвестного или несовместимого класса/единиц/модели возвращается count=null и структурированная причина. AS/RS не получает число 150 из старой маршрутной формулы.

Нулевое количество допустимо как результат sizing при отсутствии потока и резерва, но не создаёт экономический сценарий роботизации с экономией персонала.

Специализированные модели AS/RS, стационарных ячеек, уборки и инспекций оставлены следующему этапу. Формы основных демо ещё не содержат всех новых параметров цикла; до их предметного заполнения количество неизвестно.

DSL технических правил разбирает обе логические ветви, корректно обрабатывает аргументы min/max/round и арифметические ошибки. В формулах десятичный разделитель — точка, запятая — разделитель аргументов; в числовых входных значениях остаётся поддержка десятичной запятой. Нечисловой/бесконечный результат и отрицательное/дробное количество машин отклоняются.

## Публичный контракт

Сохранены pass/conditional/unknown/fail, notes, best_product_id, count/count_note. Добавлены:

- reasons: code/message/severity/field/stage;
- technical_ready, sizing_ready, economic_ready;
- sizing.model/reasons, economic_reasons;
- selection_policy=confirmed_economic_ready_v1.

`best_product_id` относится только к подтверждённому экономически готовому кандидату. Conditional и unknown автоматически не включаются в парк. Conditional можно оставить в сравнении, но до разрешения ограничений он не участвует в обычной экономике. Исследовательского режима с подменой количества/цены на этом этапе нет.

Отсутствие picks означает автоматический выбор; `picks={}` — явно пустой парк. Choices остаётся картой явных замен для автоматического режима. Невалидный сохранённый или переданный ID не заменяется другим молча. Сервер возвращает selection_invalid и неполный результат даже при обходе интерфейса. Для частично выбранного набора непокрытые включённые процессы проекта перечисляются в blockers.

Экономика возвращает status=complete/incomplete, complete, equipment_complete, labor_baseline_complete, blockers, coverage, selection_mode и scope=project. Если неизвестны парк/количество/комплект/цена или покрытие, итоговые финансовые figures имеют value=null, available=false, нет графика денежных потоков/подсказок окупаемости. Полностью известные отдельные позиции могут сохранять стоимость, но не выдаются за итог проекта. Если известны оборудование и цена, но не исходный труд, CAPEX может быть известен; ROI/payback/TCO и итоговые годовые затраты остаются неизвестными.

`annual_cost` теперь допускает null: клиент должен проверять status/available и nullable figures. Неполный расчёт возвращается HTTP 200 с диагностикой, а не ошибкой сервера. Количество null никогда не заменяется единицей. Исходные FTE больше не выводятся из числа роботов. Нормативы финансовых сценариев сохранены и остаются допущениями.

Frontend использует ту же политику допуска. Устаревшие выборы сохраняются для диагностики, экономически непригодный кандидат не может быть выбран кнопкой. Повреждённые структуры localStorage нормализуются. Неполный расчёт обозначен на экономике/what-if и в экспортируемом дисклеймере; переход к нему доступен и при пустом подтверждённом парке.

## Миграция и воспроизводимость

`0024_assessment_profiles` создаёт две таблицы и загружает фиксированный `0024_assessment_seed.json`: 29 точечных документов по сохранённым свидетельствам и 8 профилей ограничений процессов. Полная достаточность реальных профилей не объявлена подтверждённой. Сведения об операторском исполнении, внешней авиационной среде, системном уровне, зависимостях и семействах используются общими правилами; в алгоритме нет blacklist UUID.

Карточки, ТТХ, источники, проекты, UUID/slug и назначения не удалялись. После интеграционных проверок отдельно подтверждено равенство исходных полей всех 555 карточек, 496 связей и 605 исходных источников контрольной выгрузке. SQL-snapshot не изменён. Проверены восстановление snapshot в отдельную БД, upgrade до 0024 и обратный переход 0024→0023→0024. Новые таблицы отделены от старых ORM-сущностей, чтобы не добавлять отсутствующие колонки в запросы исторических миграций. Полный запуск без snapshot не проверялся.

Рабочие контейнеры и рабочая БД в ходе реализации не обновлялись. После проверки код вводится обычной сборкой/развёртыванием; bootstrap применит миграцию. Откат 0024 удаляет новые таблицы вместе с внесёнными в них проверками, поэтому после ручной разметки потребуется их резервная копия.

## Демо до и после

До — сохранённый контрольный прогон старого backend с picks=None; после — тот же режим на восстановленной тестовой БД. Старые количества не являются эталоном правильности.

| Демо | До: pass / conditional / unknown / fail | После: pass / conditional / unknown / fail | До: парк / CAPEX покупки | После |
|---|---|---|---|---|
| Склад | 10 / 14 / 134 / 4 | 0 / 0 / 147 / 15 | 408 / 2 916 351 288 ₽ | Нет подтверждённого парка; CAPEX/payback=null |
| Аэропорт | 3 / 10 / 137 / 0 | 0 / 0 / 141 / 9 | 8 / 42 762 341,61 ₽ | Нет подтверждённого парка; CAPEX/payback=null |
| Больница | 3 / 4 / 82 / 0 | 0 / 0 / 74 / 15 | 7 / 34 209 948,16 ₽ | Нет подтверждённого парка; CAPEX/payback=null |

Ноль в поле robots означает число включённых подтверждённых машин, а не доказанную нулевую потребность объекта. Во всех трёх случаях status=incomplete. OG-07 отклонён для внутренней медицинской доставки по среде, VOSTOK BR/SH1 — по виду/управлению, AS-RS P не получает количество по AMR-циклу. Снижение наполненности намеренно: отсутствующие подтверждения не заменены новыми догадками.

Контрольные материалы в Git: `platform/tests/fixtures/matching-before-stage1.json`, `matching-after-stage1.json`, `fleet-selection.json`. Повторить снимок после миграции: из platform выполнить `PYTHONPATH=. python tools/check_assessment_demos.py`. Скрипт использует READ ONLY-транзакцию и не вызывает HTTP match с учётом показов.

## Проверки и дальнейшие ограничения

- 228 backend-тестов прошли на отдельной PostgreSQL, включая тесты API/БД и положительный полностью заданный синтетический комплект.
- Общий набор выбора проходит в Python и TypeScript; frontend проверяет также числовые границы и старое localStorage.
- Пройдены 20 проверок test:sim, typecheck и production build frontend; 9 общих сценариев выбора проверены в Python и TypeScript.
- Проверен цикл downgrade/upgrade миграции на тестовой БД. Рабочие данные и snapshot не менялись.
- Браузерный E2E, нагрузка и запуск без snapshot не проверялись.

Изменения не делают весь каталог достоверным. Не выполнены массовая дедупликация, классификация всех карточек, заполнение ТТХ, специализированные модели мощности, оптимизация TCO/ранжирования и история AssessmentRun. Профили и price_complete требуют предметного подтверждения с первичными источниками. Административный API для этого уже есть; полноценный редактор новых профилей в UI оставлен следующему этапу. Сохранённые финансовые нормативы, распределение труда по операциям и модель совместного ресурса требуют отдельной проверки.
