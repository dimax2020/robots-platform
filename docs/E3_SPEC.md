# E3: контракт подбора роботов

Документ фиксирует границы работ этапа E3 — подбор, расчёт количества и объяснимый скоринг. Экономика (`cost.py`), планировка (`layout.py`), имитация (`sim.py`), Монте-Карло (`mc.py`) и оптимизатор (`optimize.py`) остаются заглушками.

Всё, что здесь написано, обязательно. Если реализация расходится со спецификацией — правится реализация, а не спецификация. Если спецификация противоречит сама себе или чего-то не хватает — сообщить, не додумывать.

---

## 0. Принципы, из которых всё следует

1. **Ни одного числа без источника.** ТЗ 3.5.1: «использование недокументированных коэффициентов не допускается». Каждый норматив имеет строку в `source` с непустым `rationale`. Каждое число, попадающее в интерфейс, имеет запись в `trace[]` с формулой и источником.
2. **Отсутствие данных — это `unknown`, а не `fail`.** Продукт не виноват, что вендор не опубликовал характеристику. Жёсткое исключение только при доказанном нарушении ограничения (ТЗ 3.4.3).
3. **Каталог остаётся честным.** Подстановки лестницы достоверности выполняются в момент расчёта и никогда не записываются в `product.attrs`. В карточке продукта пусто значит пусто.
4. **Заглушка видна, а не замаскирована.** Если правил нет или входа не хватает — это отдельная запись в трассировке, а не молчаливый ноль.

## 1. Разделение ответственности за пробелы в данных

Ключевое правило E3, из него следует поведение всего конвейера:

| Где участвует поле | Поля нет или `status="unknown"` | Обоснование |
|---|---|---|
| в **жёстком правиле** (`hard`) | предикат даёт `unknown` → продукт в корзину «требует проверки», количество **не считаем**, формируем `VendorQuery` | ТЗ 3.4.2, 3.4.3 |
| только во **входе формулы** (`sizing`) | лестница достоверности, количество **считаем**, достоверность падает до C или D | ТЗ 7.5, Дополнения §4 |

Одно и то же поле может быть и в `hard`, и в `sizing` (например `payload_kg`). Тогда работает первая строка: пока жёсткая проверка не прошла, до расчёта количества дело не доходит.

## 2. Лестница достоверности

Три ступени, строго в этом порядке. Ступень фиксируется в `Resolved.origin` и в трассировке.

| Ступень | Условие | Достоверность | `origin` |
|---|---|---|---|
| 1. Значение продукта | `product.attrs[key].status == "known"` и значение приводится к числу | по `source.kind` продукта | `vendor` |
| 2. Медиана по классу | не меньше `analogue_min_sample` продуктов с известным значением в том же `solution_type_code`; если не хватает — расширяем до `family` | `C` | `analogue_median` |
| 3. Норматив-допущение | `calc_norm` с ключом `default.<attr_key>.<family>`, затем `default.<attr_key>` | `D` | `assumption_norm` |

Если не сработала ни одна ступень — резолвер возвращает `None`. Вызывающий шаг обязан записать `TraceStep` с `verdict="unknown"` и внятным сообщением, а продукт для этой задачи не подбирать.

Достоверность выводится из `source.kind`, нигде не хранится:

| `source.kind` | буква |
|---|---|
| `vendor` | A |
| `dealer`, `media`, `catalog` | B |
| `analogue` | C |
| `assumption` | D |

Медианы считаются один раз при создании резолвера, не в цикле по продуктам.

## 3. Реестр нормативов

Все нормативы живут в `data/norms/calc_norms.json`, сеются в таблицу `calc_norm`. E3 заводит только нормативы подбора и расчёта количества; экономические (`integration_pct`, `service_pct`, `energy_tariff` и прочие) — этап E4, сейчас их не создаём.

### 3.1 Соглашение об именах

- **Плоские ключи без точек** — всё, на что ссылаются выражения RuleSpec через `norm.<key>`. Точка в имени сломает разбор выражения, потому что `norm.a.b` читается как вложенный словарь.
- **Точечные ключи** — только дефолты лестницы достоверности и профилей объектов. В выражениях RuleSpec не встречаются, их читает резолвер по имени.

### 3.2 Общие коэффициенты (`solution_type_code = null`, плоские)

| Ключ | Единица | Смысл | Где используется |
|---|---|---|---|
| `k_util` | доля | коэффициент загрузки | все семейства |
| `n_reserve` | шт | резерв парка, прибавляется к результату | все семейства |
| `t_wait_s` | с | ожидание в цикле: разъезды, лифты, очередь на зарядку | `flow_cycle` |
| `f_passes` | раз | число проходов по площади за окно | `area_window` |
| `f_frequency` | раз | частота инвентаризации за окно | `count_window` |
| `rounds_required` | шт | требуемых обходов за окно | `perimeter_rounds` |
| `n_stops` | шт | остановок за обход | `perimeter_rounds` |
| `t_stop_s` | с | длительность остановки | `perimeter_rounds` |
| `trl_min_automatch` | УГТ | ниже этого значения продукт вне автоподбора | `match` |
| `analogue_min_sample` | шт | минимум позиций для медианы по классу | резолвер |

### 3.3 Дефолты входов формулы (точечные)

Формат: `default.<attr_key>` или `default.<attr_key>.<family>`. Семейный вариант имеет приоритет.

Обязательный минимум, без которого расчёт не поедет (по данным покрытия ТТХ):

`default.charge_time_h.flow_cycle`, `default.charge_time_h.area_window`, `default.charge_time_h.station_robots`, `default.work_time_h.flow_cycle`, `default.speed_loaded_ms.flow_cycle`, `default.speed_empty_ms.perimeter_rounds`, `default.robots_per_station`, `default.throughput.area_window`, `default.t_load_s`, `default.t_unload_s`.

`default.robots_per_station` равен 1: у крана-штабелёра и шаттла один робот на позицию, множитель больше единицы бывает только у кубического хранения.

### 3.4 Дефолты профиля объекта (точечные)

Формат: `default.site.<field>.<object_type_code>`, затем `default.site.<field>`.

Обязательно закрыть то, чего нет в датасете: `default.site.shift_hours.airport`, `default.site.shifts_per_day.airport`, `default.site.days_year.airport`, `default.site.shift_hours.hospital`, `default.site.clean_area_share` (доля убираемой площади от общей, если убираемая не задана).

### 3.5 Требования к каждой записи

```json
{
  "key": "k_util",
  "value": 0.82,
  "unit": "доля",
  "solution_type_code": null,
  "editable": true,
  "source": {
    "kind": "assumption",
    "publisher": "Команда платформы",
    "rationale": "Здесь — откуда взято число, чем обосновано и почему именно столько"
  }
}
```

`rationale` обязателен и непуст. Формулировки вида «принято экспертно» недостаточно: нужна причина. `editable: false` только там, где правка пользователем ломает смысл расчёта.

## 4. RuleSpec

### 4.1 Структура и наследование

Модели `HardRule`, `SoftRule`, `Sizing`, `RuleSpec` уже описаны в [backend/engine/rules.py](../backend/engine/rules.py) и не меняются.

Файлы правил:

- `data/rules/_family_<family>.json` — шаблон семейства, пять файлов
- `data/rules/<solution_type_code>.json` — переопределение конкретного типа решения
- `data/rules/_default.json` — существующий плейсхолдер, остаётся для типов без шаблона

Разрешение при сиде: файл типа решения, иначе шаблон его семейства, иначе `_default`. Поле `solution_type` в итоговом объекте всегда перезаписывается кодом типа решения, `sizing.family` — семейством типа решения.

Переопределения пишем только для типов решений, привязанных к складу, аэропорту и медучреждению. Остальные наследуют шаблон семейства.

### 4.2 Контекст выражений

`evaluate(expr, ctx)` получает словарь с четырьмя корнями:

| Корень | Содержимое |
|---|---|
| `task` | поля `Task`, уже подготовленные (см. §6.1) |
| `site` | поля `SiteProfile`, уже подготовленные |
| `robot` | плоский словарь `attr_key -> float`, значения после лестницы достоверности |
| `norm` | плоский словарь `key -> float`, только ключи без точек |

Ограничения вычислителя, которые нельзя обойти: нет `and`, `or`, `not`, нет тернарного оператора, нет списков и индексации. Из функций доступны `ceil`, `floor`, `min`, `max`, `abs`. Логику выбора выражать арифметикой либо переносить в Python.

### 4.3 `HardRule`

- `field` — ключ характеристики продукта из `data/attributes.json`
- `op` — один из `>=`, `<=`, `>`, `<`, `==`, `!=`
- `ref` — **выражение**, вычисляемое тем же `evaluate()` в том же контексте. Поэтому допустимо `site.storage_height_m * 1000` и `min(task.max_load_kg, 1500)`

Оператор `in` вычислителем не поддерживается: `ast.In` и списки не входят в белый список. В E3 его не используем.

### 4.4 `SoftRule` и псевдополя

`field` — либо ключ характеристики, либо одно из псевдополей, которые вычисляет `rank.py`:

| Псевдополе | Значение | Тип |
|---|---|---|
| `trl` | `product.trl`, пусто трактуется как 0 | число, `dir` |
| `availability` | `product.availability` | строка, `map` |
| `reliability` | худшая достоверность среди значений, участвовавших в расчёте количества этого продукта | строка A–D, `map` |
| `has_case` | 1, если у продукта есть кейс по процессу задачи, иначе 0 | число, `dir` |
| `data_completeness` | доля заполненных характеристик продукта, 0..1 | число, `dir` |

Сумма веса всех `soft` в одном RuleSpec должна равняться 1.0 с точностью до 0.001. Это проверяется приёмкой.

### 4.5 Формулы семейств

Канон — Architecure §7.3 с `t_wait` и `n_reserve`. Основание: ТЗ 3.5.2 требует учесть «загрузки, доступности и резерва».

`vars` вычисляются **в порядке объявления**, каждая следующая видит предыдущие. Это обязательное свойство реализации `size.py`.

**`flow_cycle`** — транспорт, доставка, штабелёры, тягачи, комплектовщики:

```json
{
  "vars": {
    "t_cycle": "2 * task.route_len_m / robot.speed_loaded_ms + task.t_load_s + task.t_unload_s + norm.t_wait_s",
    "uptime": "robot.work_time_h / (robot.work_time_h + robot.charge_time_h)",
    "q": "3600 / t_cycle * uptime * norm.k_util"
  },
  "formula": "ceil(task.flow_per_hour / q) + norm.n_reserve"
}
```

**`area_window`** — уборка:

```json
{
  "vars": {
    "t_window": "site.shift_hours * site.shifts_per_day",
    "q": "robot.throughput * norm.k_util"
  },
  "formula": "ceil(site.clean_area_m2 * norm.f_passes / (q * t_window)) + norm.n_reserve"
}
```

**`count_window`** — инвентаризация:

```json
{
  "vars": {
    "t_window": "site.shift_hours * site.shifts_per_day",
    "q": "robot.throughput * norm.k_util"
  },
  "formula": "ceil(site.pallet_places * norm.f_frequency / (q * t_window)) + norm.n_reserve"
}
```

**`station_robots`** — автоматизированное хранение. Три подварианта Architecure (кубическое, шаттловое, кран-штабелёр) сводятся к одному выражению через `robots_per_station`: у крана и шаттла он равен единице, у кубического хранения больше:

```json
{
  "vars": {
    "stations": "ceil(task.flow_per_hour / (robot.throughput * norm.k_util))"
  },
  "formula": "ceil(stations * robot.robots_per_station) + norm.n_reserve"
}
```

Вспомогательное оборудование (шахты, каналы, проходы, погрузчики для постановки шаттла) в E3 не считаем. Это часть требования ТЗ 3.5.2 про «вспомогательное оборудование», она отложена вместе с экономикой.

**`perimeter_rounds`** — охрана, патрулирование, облёты. Единицы согласованы: обе части в секундах:

```json
{
  "vars": {
    "t_round": "task.route_len_m / robot.speed_empty_ms + norm.n_stops * norm.t_stop_s",
    "t_window": "site.shift_hours * site.shifts_per_day * 3600"
  },
  "formula": "ceil(norm.rounds_required * t_round / (t_window * norm.k_util)) + norm.n_reserve"
}
```

### 4.6 Жёсткие правила по семействам

Минимальный набор шаблонов. Конкретные типы решений добавляют свои.

| Семейство | Правила |
|---|---|
| `flow_cycle` | `payload_kg >= task.max_load_kg`, `min_aisle_width_m <= site.aisle_width_m`, `temp_min_c <= site.temp_min_c`, `temp_max_c >= site.temp_max_c`, `floor_load_kg_m2 <= site.floor_load_kg_m2` |
| `area_window` | `min_aisle_width_m <= site.aisle_width_m`, `temp_min_c <= site.temp_min_c` |
| `station_robots` | `payload_kg >= task.max_load_kg`, `temp_min_c <= site.temp_min_c` |
| `count_window` | `min_aisle_width_m <= site.aisle_width_m`, `lift_height_mm >= site.storage_height_m * 1000` |
| `perimeter_rounds` | `temp_min_c <= site.temp_min_c`, `temp_max_c >= site.temp_max_c` |

Если правая часть (`ref`) не определена в профиле объекта, правило **пропускается** без вердикта: ограничения площадки нет, значит и нарушать нечего. Это фиксируется записью в трассировке, чтобы пропуск был виден.

### 4.7 Веса скоринга по умолчанию

Одинаковы для всех шаблонов семейств, сумма 1.0:

| Поле | Вес | Правило |
|---|---|---|
| `trl` | 0.25 | `dir: max` |
| `availability` | 0.20 | `map: {"operation": 1.0, "piloting": 0.5, "rnd": 0.0}` |
| `reliability` | 0.20 | `map: {"A": 1.0, "B": 0.7, "C": 0.35, "D": 0.1}` |
| `price_rub` | 0.20 | `dir: min` |
| `has_case` | 0.15 | `dir: max` |

## 6. Поведение шагов конвейера

### 6.1 Подготовка входа

Выполняется в начале `size.py`, результат используется и формулами, и жёсткими правилами.

**Часовой поток.** Если `task.flow_per_hour` не задан, а `flow_per_day` есть:

```
flow_per_hour = flow_per_day / (site.shift_hours * site.shifts_per_day) * peak
```

где `peak` — `task.peak_factor`, иначе `site.peak_factor`. Обязательна запись в трассировке с подставленными числами: это преобразование, а не данные.

**Время погрузки и разгрузки.** `t_load_s` и `t_unload_s` равные нулю считаются незаполненными и берутся из `default.t_load_s` и `default.t_unload_s`.

**Профиль объекта.** Пустые `shift_hours`, `shifts_per_day`, `days_year`, `clean_area_m2` берутся через лестницу из точечных нормативов §3.4.

### 6.2 `match.py`

```python
def run(req: CalcRequest, catalog: Catalog) -> tuple[list[Candidate], list[TraceStep]]
```

Порядок:

1. Для каждой задачи взять коды типов решений из `catalog.process_solutions[task.process_code]`. Если процесса нет в карте — запись в трассировке, задача пропускается.
2. Отобрать продукты этих типов решений.
3. Порог автоподбора: `availability == "rnd"` или `trl < norm.trl_min_automatch` или `trl is None` → продукт исключается из автоподбора и кандидатом не становится. Исключение: продукт из `req.manual_product_ids` проходит дальше, и по нему пишется предупреждающая запись трассировки (ТЗ 3.4.4).
4. Для каждого продукта прогнать все `hard` из его RuleSpec трёхзначным предикатом:
   - `ref` не вычисляется (нет данных площадки) → правило пропущено, запись в трассировке, на вердикт не влияет
   - значения продукта нет или `status == "unknown"` → `unknown`, ключ в `Candidate.unknown`
   - `status == "not_applicable"` → `pass`
   - иначе сравнение: `pass` или `fail`, при `fail` ключ в `Candidate.failed`
5. Вердикт продукта: есть хотя бы один `fail` → `fail`; иначе есть `unknown` → `unknown`; иначе `pass`.
6. `VendorQuery` формируется на каждое поле из `Candidate.unknown` при вердикте `unknown`. `source_url` — `url` источника продукта, если есть.

Один `Candidate` на пару продукт и процесс. `score` на этом шаге остаётся `None`, его заполняет `rank.py`.

### 6.3 `size.py`

```python
def run(req, candidates, options_unused, catalog, norms) -> tuple[list[SizedOption], list[TraceStep]]
```

Сигнатура не меняется. Считаем количество только для кандидатов с `verdict == "pass"`.

1. Подготовить вход (§6.1).
2. Собрать контекст: `task`, `site`, `norm` (плоские ключи), `robot` — значения через резолвер по всем ключам, которые встречаются в `vars` и `formula` этого RuleSpec.
3. Вычислить `vars` в порядке объявления, затем `formula`.
4. Результат привести к целому, не меньше 1. Ноль или отрицательное — признак битой формулы: запись в трассировке и пропуск, а не молчаливая единица.
5. Защита от деления на ноль: если любое разрешённое значение равно нулю там, где стоит в знаменателе, — запись в трассировке и пропуск продукта.

`SizedOption.formula` содержит выражение **с подставленными числами**, например `ceil(147.5 / 12.4) + 1 = 13`.

Трассировка: одна запись на итог расчёта количества и по одной записи на каждый вход, полученный со ступени `analogue_median` или `assumption_norm`. Входы со ступени `vendor` отдельными записями не дублируем — они видны в подставленной формуле.

### 6.4 `rank.py`

```python
def run(req, candidates, options, catalog, norms) -> tuple[list[Scenario], list[TraceStep]]
```

1. Посчитать `score` каждого кандидата с `verdict == "pass"` по `soft` его RuleSpec.
2. Нормировка `dir`: min-max по множеству кандидатов **того же процесса** — сравниваются только сопоставимые альтернативы. `dir: max` → `(v - min) / (max - min)`, `dir: min` → обратное. Разброс нулевой → фактор даёт 1.0.
3. Нормировка `map`: значение по ключу, отсутствующий ключ → 0.0.
4. `score` = взвешенная сумма, диапазон 0..1.
5. Трассировка: по одной записи на каждый фактор каждого кандидата, с весом, нормированным значением и вкладом в итог (ТЗ 3.4.5).
6. Сценарии: возвращаем три как сейчас. `per_task` наполняется составом — лучший по `score` продукт на каждый процесс со своим количеством из `options`. `baseline` и `optimal` остаются пустыми, `economics` у всех `None`: экономика — этап E4.

`Candidate.score` мутируется на месте либо кандидаты пересобираются — важно, что в ответе `score` заполнен.

### 6.5 `pipeline.py`

Передать `norms` в шаги, которые их ждут, и заполнить `vendor_queries` вместо жёсткого `[]`. Проще всего — вернуть запросы из `match.run` третьим элементом или собрать их в `pipeline` из `candidates`. Выбранный вариант описать в докстринге.

## 7. API

### 7.1 Новый роутер проектов

Префикс `/api/v1/projects`. Таблицы `project` и `calc_run` уже существуют, миграция не нужна.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /projects` | `{name, object_type_code, industry_code?, use_demo?}` | проект с предзаполненными `site` и `tasks` из профиля объекта |
| `GET /projects` | — | список проектов |
| `GET /projects/{id}` | — | проект |
| `PATCH /projects/{id}` | `{name?, site?, tasks?, overrides?}` | обновлённый проект |
| `POST /projects/{id}/calculate` | — | `CalcResponse`, прогон сохраняется в `calc_run` |
| `GET /projects/{id}/runs/latest` | — | последний сохранённый `CalcResponse` или 404 |

Плюс справочник для формы создания: `GET /api/v1/refs/site-profiles/{object_type_code}` отдаёт профиль по умолчанию из `data/site_profiles/`.

`project.owner_id` ссылается на `app_user` и не может быть пустым. Сеем одного демо-пользователя с фиксированным UUID, роль `admin`, все проекты его. Авторизации в E3 нет.

Существующий `POST /api/v1/calculate` остаётся без изменений — это расчёт без сохранения.

### 7.2 Снимок каталога

`app.state.catalog` читается один раз в lifespan, поэтому правки ТТХ в админке в расчёт не попадают. Добавить `POST /api/v1/admin/catalog/reload`, который перечитывает снимок, и вызывать `validate_rule_spec` при загрузке — битое правило должно падать на старте, а не в расчёте.

## 8. Фронтенд

### 8.1 Композабл

`frontend/app/composables/useCalc.ts` в стиле [useCatalog.ts](../frontend/app/composables/useCatalog.ts): `useAsyncData` плюс `$fetch`, база через `useApiBase()`, отображение snake_case в view-модель в том же файле. Типы ответа расчёта дописать в `frontend/app/types/api.ts`.

### 8.2 Корзины подбора

Выводятся из `candidates`, а не приходят с сервера:

| Корзина | Условие |
|---|---|
| Подходит | `verdict === 'pass'` |
| Требует проверки | `verdict === 'unknown'` |
| Исключено | `verdict === 'fail'` |

Количество на строке — join `options` по паре `product_id` и `process_code`. Карточка продукта — join с каталогом из `useCatalog()` по `product_id`. Человеческие подписи ключей из `failed` и `unknown` — из `attribute_def.label`, ключ без подписи показывать как есть.

Объяснение строки — записи `trace` с этим `product_id`, сгруппированные по `step`. Источник рисуем существующим `UiSourceTag`, формулу — существующим оформлением `<code class="formula">`.

### 8.3 Что убрать и что не трогать

Убрать из `frontend/app/data/projects.ts` только `matchFit`, `matchCheck`, `matchExcluded` и тип `MatchRow`. `scenarios`, `capexLines`, `opexLines`, `effectLines`, `norms` остаются: страницы сценариев, экономики и what-if продолжают жить на моках до этапа E4. Ломать их нельзя.

### 8.4 Форма параметров

`params.vue` сейчас показывает поля через `:value` без `v-model`, правки теряются. Сделать двустороннее связывание, предзаполнение из `site` проекта, сохранение через `PATCH /projects/{id}`. Кнопка «Запустить подбор» вызывает `POST /projects/{id}/calculate` и ведёт на `/match`.

## 9. Формат трассировки

`TraceStep.message` — человеческая фраза по-русски, её читает пользователь. `formula` — выражение с подставленными числами. `source` — строка формата `[буква] краткий источник`:

| Ступень | Пример `source` |
|---|---|
| значение продукта | `[A] ronavi-robotics.ru/catalogue/h1500` |
| медиана по классу | `[C] медиана по классу amr_pallet, 6 позиций` |
| норматив-допущение | `[D] допущение: default.charge_time_h.flow_cycle = 2` |

Обязательные записи по шагам:

| Шаг | Записи |
|---|---|
| `match` | на каждый прогнанный `hard`-предикат: поле, сравнение, вердикт. На каждое пропущенное правило. На каждый продукт вне автоподбора, добавленный вручную |
| `size` | на преобразование суточного потока в часовой. На каждый вход со ступени C или D. На итоговое количество с полной подставленной формулой |
| `rank` | на каждый фактор каждого кандидата: вес, нормированное значение, вклад |

## 10. Приёмка этапа

1. `uv run pytest` в `backend/` проходит, включая новые тесты: трёхзначный предикат, все пять формул семейств, три ступени лестницы, нормировка скоринга.
2. `python -m scripts.seed --reset` наполняет `calc_norm` и проставляет непустые RuleSpec.
3. `POST /api/v1/calculate` со складским профилем из датасета возвращает непустые `candidates`, непустой состав в сценарии `per_task`, непустой `trace`.
4. В браузере: создание проекта, правка параметров, запуск подбора, три корзины с раскрываемым объяснением, формулой и источником в каждой строке.
5. Ни одного числа в интерфейсе без соответствующей записи в трассировке.
