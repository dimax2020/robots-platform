Добавлена обработка записей с отдельными условиями и режимами. Данные с разными
условиями сохраняются раздельно: время без нагрузки и с полной нагрузкой, а также
статическая грузоподъёмность и грузоподъёмность в движении. Для расчёта работы
используется время под полной нагрузкой; для перевозки — грузоподъёмность в
движении. Например, `12 ч без нагрузки / 6 ч с полной нагрузкой` даёт отдельные
значения `12 ч` и `6 ч`, а расчётное `work_time_h` равно `6 ч`.

Автоматически обрабатываются приблизительные значения, повторы парсера, варианты
написания единиц и невидимые символы, верхние границы с пояснением, зарядка в
строке со временем работы, объём бака в поле грузоподъёмности и нагрузка на один
ярус. Признак приблизительности и пояснения сохраняются; «до 90%» хранится как
отдельное время зарядки, а не как полный заряд. Значения без единиц, разные
варианты и описания без числа не превращаются в догадки.

## Предыдущий этап: верхняя граница диапазона

По согласованному правилу теперь **берём верхнюю границу**:

- `до 3 часов` → `3 ч`;
- `2–4 часа`, `от 2 до 4 часов`, `2~4 ч` → `4 ч`;
- `120–240 минут` → `4 ч`;
- `до 90 минут` → `1.5 ч`;
- `90 мин – 2 ч` → `2 ч`.

Поддержаны дефис, короткое/длинное тире, тильда, десятичная запятая,
«не более», `≤` и `<=`. Единицы пересчитываются после выбора верхней границы
с учётом единиц обоих концов диапазона. Правило также используется в формулах.
Исходное значение остаётся в исходном атрибуте либо `normalization_original`;
преобразованное поле отмечается `normalization_rule: upper_bound`.
Защита ручных значений и проверка конфликтующих источников сохраняются.

**Применено к локальной БД: дополнительно обновлены 58 из 555 карточек.**

## Откуда берётся каталог

Публичные карточки и сравнение используют `platform`, а не старый `backend`.

1. На пустой БД `platform/app/bootstrap.py` восстанавливает
   `platform/seed/platform.sql`, затем выполняет миграции.
2. Последующие импорты CSV и результаты парсеров проходят через
   `platform/app/worker.py` → `platform/app/infrastructure/db/ingest.py`.
3. Технические значения хранятся в `product.attrs`, подписи и единицы — в
   `attribute_def`. Исходные данные парсеров и сведения об источниках сохраняются.
4. Новая миграция `0009_normalize_attributes` обрабатывает уже существующие данные,
   в том числе восстановленные из старого SQL-снимка. Сам снимок вручную не переписан.

Открытый в IDE `data/catalog_normalized.json` обслуживает прежний контур:
CSV организатора → `backend/scripts/normalize.py` → этот JSON →
`backend/scripts/seed.py`. Его характеристики дополняют `import_ttx.py` и
`import_robots.py`. Эти старые файлы не являются источником текущей карточки и
в рамках изменения не переписывались. Команда `make normalize` по-прежнему относится
к старому контуру; для платформы добавлены отдельные команды ниже.

## Что исправлено

### Общая нормализация

`platform/app/domain/specs.py` теперь содержит общие правила для импорта парсеров,
CSV ручных ТТХ, правок карточек администратором и обработки существующей БД.
Русские названия, типы, группы и базовые единицы берутся из
`platform/seed/attributes.json`.

Поддерживаются явные алиасы ключей и известные подписи:

| Исходное значение | Результат |
|---|---|
| `charge_min = 90` | `charge_time_h = 1.5`, ч |
| Время зарядки, мин: `90` | `charge_time_h = 1.5`, ч |
| Время заряда батареи, час.: `1,5` | `charge_time_h = 1.5`, ч |
| Время работы: `7200 сек` | `work_time_h = 2`, ч |
| Максимальная скорость: `3,6 км/ч` | `max_speed_ms = 1`, м/с |
| Грузоподъёмность: `1,5 т` | `payload_kg = 1500`, кг |
| Масса, г: `500` | `mass_kg = 0.5`, кг |
| Минимальная ширина прохода: `700 мм` | `min_aisle_width_m = 0.7`, м |
| `lift_height_m = 2.5` | `lift_height_mm = 2500`, мм |
| Габариты: `10 × 20 × 30 см` | `dimensions_mm = "100 × 200 × 300"`, мм |

Также поддерживаются м/мин, часы/минуты/секунды, граммы/килограммы/тонны,
метры/сантиметры/миллиметры, Вт/кВт для известных соответствующих полей,
десятичная запятая и пробелы-разделители тысяч.
Единица в самом значении имеет приоритет; затем используются явная единица поля,
подпись, контракт алиаса или канонического ключа.
Без известной единицы у произвольного алиаса пересчёт не угадывается.

Максимальная скорость — отдельный параметр. Она не подставляется вместо скорости
с грузом. Размеры подносов, отсеков и проезда не объединяются с габаритами робота.

### Происхождение и конфликты

- У преобразованного значения сохраняются правильные `source_id` и `quote`.
  Раньше обработка сохранённых карточек могла брать первый источник из карточки.
- Исходные алиасы физически остаются в `attrs`, чтобы сохранить данные и не ломать
  существующие формулы, которые читают старые ключи. Если значения эквивалентны,
  алиас получает `alias_of` и не создаёт дубликат в карточке, сравнении и редакторе.
- Исходная запись преобразованного канонического поля хранится в
  `normalization_original`; исправленное старое значение — в
  `normalization_previous`; источник преобразования — в `normalized_from`.
- Разные значения из разных источников не объединяются молча. Они остаются
  доступными, конфликт записывается в отчёт.
- Подтверждённые ручные значения защищены. Повторный импорт обновляет значение,
  ранее выведенное из того же поля и источника, но не чужую ручную правку.
- Статус `not_applicable` сохраняется; конфликт с известным значением учитывается.
- Удаление канонического значения в редакторе удаляет и его скрытые эквивалентные
  алиасы, чтобы удалённое поле не восстанавливалось из них сразу же.

### Подписи и интерфейс

- Справочник дополнен максимальной скоростью, видом робота и метаданными каталога.
- Метаданные восстанавливаются при запуске и для непустой БД. Исправление
  технической подписи больше не пропускается из-за уже заполненной группы.
- Нормальные пользовательские подписи не перезаписываются.
- Новая характеристика с неизвестным техническим ключом требует понятной подписи
  `label` либо записи в справочнике. Импорт с отсутствующей подписью сообщает об
  ошибке вместо создания очередного `some_field_attr` на странице.
- Ручной CSV понимает необязательные столбцы `label` и `unit`. Прежний формат
  с известными ключами продолжает работать.
- Публичный API возвращает единицу, карточка и сравнение показывают её рядом с
  числом. Если исходный текст уже содержит единицы, они не дублируются.
- Разбор чисел в формулах больше не выбирает первое число диапазона или первого
  из нескольких режимов. Исправлена потеря знака у отрицательных чисел.
