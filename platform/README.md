# Платформа каталога

Новый бэкенд каталога и подбора. Старый `backend/` и его база `robots` не используются этим сервисом и не удаляются.

## Что делает эта версия

Карточка робота собирается из трёх входов, и у каждого значения остаётся источник.

- Исходный каталог ФЦ БАС, файл `catalog_export_v4.csv`, как он есть. Все колонки строки сохраняются. Сценарий и отрасль из файла не назначают роботу процесс.
- Ручная таблица `ttx_manual.csv`. Она дописывает пустые характеристики уже существующей карточки и не затирает заполненное каталогом. Источник берётся из строки таблицы.
- Парсеры `robob2b`, `robort` и `robot.moscow`. Они отдают карточки в общий ingest и сами в базу не пишут. `robot.moscow` читает HTML `https://robot.moscow/catalog` и берёт только роботов с ценой.

Подбор идёт по процессам объекта. У процесса свои фильтры: какие поля площадки сравнить с какими характеристиками робота. Вердикты: подходит, подходит с условием, уточнить у вендора, не подходит. Бюджет и окупаемость не отсекают. Расчёт количества, экономика, сравнение и what-if остаются на старом API.

Список каталога отдаётся порциями с курсором. Полный JSON характеристик читается только у одной карточки.

## Слои

Зависимости идут в одну сторону.

- `app/domain` — типы, разбор CSV и функция подбора. Базы и HTTP здесь нет.
- `app/application` — сид склада.
- `app/infrastructure/db` — Postgres: карточки, таксономия, очередь `job`.
- `app/parsers` — модули обхода сайтов. Новый источник — новый модуль в `PARSERS`.
- `app/api` — HTTP.
- `app/worker.py` — забирает прогоны. Очередь — таблица `job`, захват через `FOR UPDATE SKIP LOCKED`. Redis нет.

Два процесса из одного образа: `platform-api` принимает запросы, `platform-worker` выполняет импорт и парсеры. Ручка импорта сразу отвечает `job_id`. Повторный запуск того же прогона, пока он идёт, не стартует второй.

Пометки характеристик пересчитываются при сохранении фильтров. `active` — ключ читает фильтр, `unused` — админ отложил ключ, иначе новый ключ остаётся `pending`.

## Запуск

Сервисы `platform-api` и `platform-worker` в `docker-compose.yaml`. База `platform` создаётся в том же Postgres рядом с `robots`. Снаружи API доступен как `/platform/api/v1/...`, чтобы не перехватывать старый `/api/v1`.

```bash
docker compose up -d --build platform-api platform-worker
```

Сид склада выполняется при старте и не переписывает уже настроенный объект. Процессы склада: погрузка и паллетирование, паллетное хранение, сборка заказов, сортировка и транспорт коробов, упаковка и паллетирование, инвентаризация, мойка полов, мойка фасадов.

## HTTP

- `GET /api/v1/catalog/products?cursor=&limit=` — порция карточек без JSON характеристик и следующий курсор.
- `GET /api/v1/catalog/products/{slug}` — карточка и источники значений.
- `GET /api/v1/catalog/tree` — отрасли, объекты, процессы, фильтры и счётчики.
- `POST /api/v1/admin/imports` — форма `kind=catalog|manual` и файл, ответ `{job_id}`.
- `GET /api/v1/admin/jobs/{id}` — статус прогона.
- `GET /api/v1/admin/parsers`, `POST /api/v1/admin/parsers/{code}/runs`, `PATCH` расписания (`enabled`, `hour`, `minute`, время московское).

Импорт таблиц — экран `/admin/platform`. Парсеры — экран `/admin/parsers`: у каждого своё время суток, статус последнего прогона и кнопка «Запустить сейчас». Воркер ставит включённый парсер в очередь один раз в сутки, в течение двух часов после назначенного времени.
- `POST /api/v1/admin/objects`, `POST /api/v1/admin/processes`, `PUT /api/v1/admin/processes/{code}/filters`.
- `PUT /api/v1/admin/products/{slug}/processes` — какие процессы умеет робот.
- `POST /api/v1/projects`, `PATCH` площадки и включённых процессов, `POST /projects/{id}/match`.
